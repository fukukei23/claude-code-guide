コンテキスト節約術 — APIApplication Programming Interface（エーピーアイ）の略。あるプログラムの機能を、別のプログラムから呼び出せるようにした「窓口」消費を抑える・毎ターン課金構造と戦う

最終更新: 2026-11-10 | 起源: 2026-11-10 の GLM-5.3-Flash 週間枠23%消費事故の実測調査 この章は「実測 → 運用 → 機械化」の実践記録。基礎理論は 12_現場の知見 セクションA「コンテキスト経済学」・プロバイダー切替は 20_コスト最適化速さ・コスト・品質等の指標が良くなるように調整すること構成 が正典。

1. 課金構造の理解 — cache_read がすべての元凶

12章A「コンテキスト経済学」 で学んだ「毎ターン全文脈再送」が、実際のAPI消費としてどう現れるかの実践編。

Z.ai（GLM Coding Plan）の独自事情: cache_read もクォータフルカウント

Anthropic API のプロンプトAIに渡す指示文のこと。「この機能を作って」「この文を直して」等キャッシュ一度得た結果を取っておいて、次回は同じ計算をせず使い回す仕組み。速くなるが、元のデータが変わった時の更新忘れに注意は「キャッシュ読み取りは通常入力の1/10程度」だが、Z.ai は cache_read（キャッシュヒットした読み取り）もクォータをフルカウントする。

つまり:

状況 Anthropic 的挙動 Z.ai 的挙動
キャッシュヒットで文脈再送 割引あり（低コスト） フルカウント（割引なし）
文脈を肥大させ続ける それでもキャッシュで緩和される 消費が文脈サイズに正比例して増える

実測（2026-11-10・11-09 00:00 JST以降の transcript usage 集計）:

総消費: 927.5M tok
  cache_read: 96.4% ← ほぼすべてが「キャッシュ読み取り」
  input:       3.4%
  output:      0.3%

この 96.4% は Z.ai ダッシュボードの 96.7% Cache 表示と定量一致した。つまりこの環境の消費額のほぼ全量は「過去の会話の再送信」で占められている。

消費の読み方（実務ルール）

  • 「キャッシュ効率が良い（96% Cache）」は Anthropic では良いニュース、Z.ai では悪いニュース（=過去分の再送が大量に起きている＝文脈が肥大している）
  • 使用率の加速に気付いたら、まず疑うべきは巨大セッションClaude Codeの1回の対話単位。起動から終了までの会話と作業状態のこと。長く使うと内容が混ざるため、トピックの区切りで新セッションに引き継ぐ運用をするの存在（新規タスクを打つ＝文脈全量をもう一度送る）

2. 実測事例: 2026-11-10 の 718M 事故

何が起きたか

ふくけいが Z.ai ダッシュボードで「累計753.33M・週間23%を約4時間で到達」を視認（11-10 11:16）。調査の結果:

22:00-02:59 の4時間で 718M tok 消費。その 100% が巨大セッション3本:

セッション 消費 その後の文脈サイズ
6577（story図解） 268.2M（37%） 68.2万 tok
821a（formula-pad） 246.7M（34%） 72.3万 tok（676リクエスト・1req平均54.7万）
91ce（視角パック） 203.3M（28%） 59.9万 tok

6日間にわたり誰も気付かずセッションを継続し、文脈が60-72万tokまで成長。以後の毎ターンが「60万tokの再送」として課金され続けた。

除外確認（誤犯しやすい疑い先の実測）

  • 夜間harness（NexusCore・1回10-18万tok）→ 誤差レベル
  • durable cronクロン。Linuxで「毎日6時」「30分ごと」等の定期実行を予約する仕組み。予約実行の登録表（crontab）に書いて運用する 37件（03-09時 3-10M/h）→ 誤差レベル
  • 新セッションの固定コスト（後述11万tok）→ 日次払いで誤差

固定コストの実測: 新セッションでも約11万tok/日

新セッションの初回文脈は 10.5-11.4万 tok（3セッション実測）。内訳:

  • CLAUDE.md + rules + memory索引等のSSOT類 ≈ 11K tok = 全体の1割のみ
  • 残り9割は harness 固定部分（システムプロンプトAIに最初から組み込まれている「基本の指示書」。ユーザーの発話とは別に、AIの振る舞い方の土台を決めている。CLAUDE.md等はここに近い形で常に読み込まれる等）

→ 「セッションを区切ると固定費がかかる」は正しいが、11万tokは巨大セッションの毎ターン再送（60-72万tok×複数ターン）と比べれば誤差。

hook 差戻しリトライの単価

hook がツール実行を差戻すと、リトライ1回につき文脈全量の再送が発生する。

実測: M2.1セッション（11:38-11:46の8分）で51リクエスト・37.11M tok → 1リトライ ≈ 74万 tok（文脈が肥大した状態での発生）。

→ 巨大セッションで hook 差戻しを繰り返すと「1リトライ = 巨大な消費」になり得る。hook 設定の間違いは文脈が小さいうちに直すのが経済的。

3. 運用術 — 「日をまたぐら new-session」

採用した運用（ふくけい確定判断）

ふくけいの確定判断: 「API消費量節約を最重視。文脈サイズ＝消費単価の制御レバー」

運用 内容
日をまたぐら new-session 前回タスクから日が変わる時点で new-session スキルClaude Codeで「特定の作業手順」をパッケージ化したもの。SKILL.mdに手順を書いておくと、対応する場面でAIがその手順を読み込んで従う。経験を再利用する仕組みで引き継ぎ。文脈は自然に 20-25万 tok に収まる（作業増分は1日約10万 tok 実測）
1タスク1セッション タスクが変わったら区切る。長寿命セッションに追い打ちを掛けない
hook 差戻しは早めに潰す リトライ単価が文脈比例（74万tok実測）。文脈が小さい内に hook 設定を修正する

効果（推定・案A採用時）: 文脈を20-25万 tok に保つことで、消費は約 1/3.5 に減る。

検討で却下した案（理由込み・再提案しない）

案 内容 却下理由
案A′ 文脈 15-20万 tok で強制区切り 固定費11万 tok を引くと作業増分が4万 tok しか残らず、実運用に合わない
案D auto-compact に任せる GLMプロキシ通信の中継役。「クライアント→プロキシ→本来の宛先」の順に通信を一度経由させる仕組みで、仲介者が経路の切替・集計・制限等を担当する経由の compact 動作が未実測・コンパクション自体がトークンAIにとっての「文字数」のようなもの。AIは文章をトークンという小片に区切って処理する。課金や入力上限（コンテキストウィンドウ）はこの単位で数えられるを消費する落とし穴あり（下記節5参照）

注意: 切りすぎの悪循環

区切りすぎると handoff が粗くなり、翌日に調査やり直し＝消費増の悪循環に入る。「日をまたぐ」を基準に、タスクの状態が handoff に書ける粒度で区切るのが実運用の落とし所。

4. 機械化 — context-size-warn hook

実装設計や仕様を、実際に動くコードに作り込むこと。「実装済み」＝コードとして完成している状態済み: PostToolUse hook context-size-warn.sh

項目 値
タイミング PostToolUse（matcher=""・全ツール）
警告閾値 25万 tok 超
再警告条件 前回警告から 5万 tok 増分ごとに1回（アラート疲労対策）
強警告 50万 tok 超
state ~/.claude/state/context-size-warn/<session_id>
一時上書き CONTEXT_WARN_TH / CONTEXT_WARN_STEP 環境変数プログラムの外側（OS側）で設定する値の入れ物。プログラムを書き換えずに設定を切り替えられる。APIキー等の秘密の値はソースコードに直書きせずここに入れるのが安全な定石（テスト用）

動作例（実測・pipピップ。Pythonのライブラリ（部品）をインストールするコマンド。Pythonの買い物カートのようなものe test）: 未満=無出力 / 超過=systemMessage で「約22万 tok に達しました」表示 / 抑制=2回目は無出力。

Desktop UI の「セッションコスト（推定）」は harness 表示で CC 側から追記不可のため、この hook 経由の systemMessage 表示が代替手段。

設定時の注意（既知回避則）: settings.json に hook コマンドターミナルに入力してコンピュータに与える一行の指示。lsやcdのように『プログラム名+補足指定』で構成されるを書く際は ~ 形式の digit-free パス限定（絶対パス一番上（ルート）から数えた完全な住所のようなファイルの場所表記。「/home/…」で始まるに数字が入ると guard-settings-write 層2の TOKEN様判定で誤検知する・2026-09-29 記録済み。詳細は 00★SYSTEM/セキュリティ設定ハブ.md 参照）。

候補（未実装）: statusLine 監視

statusLine での常時表示も機械化候補だが、現状は hook の systemMessage 表示で運用開始。必要になったら本節に追記する。

12章D「よくある誤解」 の「コンパクション（compact）＝要約品質が高い」の訂正に実質を加えると: compact は要約生成のためにモデルを1回まるごと動かすため、要約の材料になった文脈全量の再送＋要約出力分の消費が発生する。「圧縮タダ」ではなく「一回払いで後続ターンの単価を下げる」操作。巨大文脈に対して実行するとその1回の消費自体が大きい。

💡 やさしい補足（初心者向け）

  • 毎ターン「過去の会話全部」をもう一度送っている: AIとの会話は「続きだけ送る」のではなく「最初から全部もう一度送る」仕組み。会話が長いほど1回の送信が重い
  • キャッシュが効いていても課金される（この環境では）: Z.aiの課金では「前回と同じ部分の読み取り」も普通の使用量として数える。つまり長い会話を続けると消費がどんどん増える
  • 対策はシンプル: 「日が変わったら会話を新しく引き継ぐ（new-session）」だけで、消費は約1/3.5に減る
  • 警告が出たら区切るサイン: 25万トークン超の警告hookが自動で教えてくれる。警告を見たら new-session の合図

💡 章の落とし所: 文脈サイズ＝消費単価の制御レバー。日をまたぐら new-session・25万 tok 警告で区切る。
