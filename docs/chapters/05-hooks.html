05 フック — イベント駆動の自動実行

💡 章の核: hookClaude Codeの特定のタイミング（ツール実行前後・セッション開始時等）で自動処理を差し込む仕組み。「保存前にチェック」「終了時に記録」等を機械的に強制できるは「LLMの約束」を機械が強制する唯一の層。事故を止めたいならここに実装設計や仕様を、実際に動くコードに作り込むこと。「実装済み」＝コードとして完成している状態する。

フックとは

フックは 特定のイベント発生時に自動実行されるシェルユーザーとOSの間に入って、コマンド入力を受け付けて実行する程序。ターミナルで打つコマンドを実際に処理する部分スクリプト自動実行できる小さなプログラム。手順を書いたテキストファイルの形をしている。Claude Codeの動作を拡張・制御する。

ユーザーがツールを実行
  │
  ▼
PreToolUse フックが発火 ──→ チェックOK → ツール実行
  │                          └─ チェックNG → ブロック
  ▼
ツールが実行される
  │
  ▼
PostToolUse フックが発火 ──→ ログ記録・後処理

主要4種のフック

<a id="sessionstart"></a>SessionStart

セッションClaude Codeの1回の対話単位。起動から終了までの会話と作業状態のこと。長く使うと内容が混ざるため、トピックの区切りで新セッションに引き継ぐ運用をする開始時に実行。

項目 説明
タイミング Claude Code起動時
用途 環境変数プログラムの外側（OS側）で設定する値の入れ物。プログラムを書き換えずに設定を切り替えられる。APIキー等の秘密の値はソースコードに直書きせずここに入れるのが安全な定石の読み込み、初期化処理、設定の検証、ハンドオフ読込
備考 なし

<a id="pretooluse"></a>PreToolUse

ツール実行前に実行。最も重要なフック。

項目 説明
タイミング 各ツール（Read, Edit, Bash等）の実行前
用途 セキュリティチェック、危険コマンドターミナルに入力してコンピュータに与える一行の指示。lsやcdのように『プログラム名+補足指定』で構成されるのブロック複数の処理が同時に同じ対象を触って衝突するのを防ぐ「鍵」の仕組み。鍵を持っている間は他の処理は待つか諦める、入力検証
備考 なし
ブロック可能 Yes — スクリプトがエラーを返すとツール実行がキャンセルされる

💡 ※2026-07-02統合撤去: 2026-06-30に追加していた minimax系MCPModel Context Protocol（エムシーピー）の略。AIに外部ツール（検索・GitHub・データベース等）を繋ぐための共通接続規格。USBのような「差せば繋がる」仕組みでAIの能力を拡張するブロック（matcher mcp__minimax-(official|video)__.*・exit 2）は、32MB真因=glm-rate-proxy client_max_size 未設定と判明（9ac5f24fd解決）したため PreToolUse hook を削除し撤去。minimax-official/video は日常セッションで即呼び可能。

現場の知見: フックのスクリプトがエラー（exit code ≠ 0）を返すと、ツールの実行がサイレントにブロックされる。意図せぬブロックに注意。→ 11_現場の知見

クロスプラットフォーム対応: フックスクリプトで python3 を直接呼ぶとWindows Git Bashで動作しない。run-security-check.sh ラッパーが python3 / python / wsl を自動検出する。Bashフックは純bashバッシュ。Linux等で使われる標準的なシェル（コマンド入力を受け付ける程序）の名前。シェルスクリプトを書く時の定番（grepグレップ。ファイルやテキストの中から、指定したパターンを含む行を抜き出すコマンド。大量のファイルから目的の言葉を探す時の定番/sed）でJSONジェイソン。データを記述する標準的な書式の1つ。設定ファイルやデータのやり取りに広く使われ、「名前: 値」の組み合わせで書く解析しpython3に依存しない。

ブロックされるコマンドの例:

  • bash -x（デバッグ不具合の原因を特定して直すこと。ログや実行の跡を辿って、どこで期待と違う動きをしたかを突き止める作業出力でシークレット露出の恐れ）
  • cat -A（特殊文字表示でシークレット露出の恐れ）
  • マスクなしの grep（APIApplication Programming Interface（エーピーアイ）の略。あるプログラムの機能を、別のプログラムから呼び出せるようにした「窓口」キーを含むファイルの検索）
  • フィルタなしの env（全環境変数値を入れておく名前付きの箱。x = 1 のように名前に値を紐付けて、後で使い回すの表示）

<a id="stop"></a>Stop

セッション終了時に実行。

項目 説明
タイミング Claude Code終了時
用途 クリーンアップ、ログ保存、ハンドオフ情報の書き出し
備考 なし

Notification / PostToolUseFailure

エラー・ブロック時（Notification）、ツール失敗時（PostToolUseFailure）に実行。Discord通知等の異常系ハンドリングに使用。

PermissionRequest（承認要求時）

承認プロンプトAIに渡す指示文のこと。「この機能を作って」「この文を直して」等が出た瞬間に実行（2026-09-29配線・notify-windows-approval.sh）。Windows側でbeep2回+MessageBoxを出す通知専用hook（async fire-and-forget）。実発火E2E済み（ask ルールでPermissionRequestを発生させて音/ポップアップを人間観測）。

⚠️ settings.jsonに書くhookコマンドは ~ 形式digit-freeに限定すること（2026-09-29実測）: guard-settings-write の層2（長文字列32字+文字種3種=TOKEN様判定）が、/home/<USER>（数字入り絶対パス一番上（ルート）から数えた完全な住所のようなファイルの場所表記。「/home/…」で始まる）や exit 2（数字）を含むコマンド文字列をTOKENと誤判定して復元する。~/.claude/... 形式（小文字+記号のみ=文字種2種）ならCLEAN通過。数字が必要な処理（exit 2への変換等）はラッパスクリプト側に分離する（実例: run-vision-pack-gate.sh）。詳細: [[01_DECIContinuous Integration（シーアイ・継続的インテグレーション）の略。コードを変更するたびに自動でテストとチェックを回し、壊れていないかを常に確認する仕組みSIONS/claude-code/2026-09-29_通知と視角パックhook配線完了-guard層2誤検知原因特定.md]]

設定方法

フックは settings.json の hooks セクションに定義する。

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ~/.claude/scripts/security/check-command-safety.py"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "source ~/.secrets.env"
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/scripts/session/save-session-log.sh",
            "timeout": 5000
          },
          {
            "type": "command",
            "command": "~/.claude/scripts/session/generate-handoff.sh",
            "timeout": 3000
          },
          {
            "type": "command",
            "command": "~/.claude/scripts/session/queue-guide-updates.sh",
            "timeout": 5000
          }
        ]
      }
    ]
  }
}

matcherについて

  • matcher はツール名を指定（例: "Bash", "Edit", "Read"）
  • 空文字 "" は全ツールにマッチ
  • 複数のフックを設定可能（配列で定義）

file_path はバックスラッシュ区切りで渡る — 判定前に正規化する（2026-08-30・重要）

tool_input.file_path を見て対象かどうかを判定する hook（Write / Edit / MultiEdit 系）は、 判定の直前でパス区切りを正規化すること。Windows Desktop 版は次の形で渡してくる。

\\wsl.localhost\Ubuntu\home\<USER>\projects\knowledge-base\01_DECISIONS\claude-code\x.md

# ❌ 素通りする（"01_DECISIONS\claude-code" なので一致しない）
case "$FILE_PATH" in *01_DECISIONS/*) ... ;; esac

# ✅ 判定の直前で正規化
FILE_PATH=$(printf '%s' "$FILE_PATH" | tr '\\' '/')
case "$FILE_PATH" in *01_DECISIONS/*) ... ;; esac

# python 側で判定する場合
fp = (ti.get("file_path", "") or "").replace("\\", "/")

⚠️ path-rewrite.py があっても直らない。あれは tool_input.command（Bash のコマンド文字列）が 対象で、tool_input.file_path は別経路なので変換されない。「Bash の hook は効くのに Write/Edit の hook だけ効かない」という症状は、matcher ではなくこの経路差が原因のことがある。

2026-08-30 時点で3つの hook がこれで素通りしていた（enforce-ssot-record.sh・ guard-config-secrets.sh・warn-naming-rules.sh）。うち guard-config-secrets.sh は 設定ファイルへの生シークレット混入を止める層だったため、実害の大きい抜けだった。

切り分けの決め手: 「matcher が効かない」と「判定が一致しない」は症状が同じに見える。 同じスクリプトに区切り違いの file_path だけを流して比較すると1回で確定する。

A: /home/.../01_DECISIONS/claude-code/x.md          → exit 2（ブロックされる）
B: \\wsl.localhost\...\01_DECISIONS\claude-code\x.md → exit 0（素通り）← 差は区切りだけ

同一エントリ内の hook は順に評価される — 対象が入れ子なら前段の通過条件に注意（2026-08-30）

1つの matcher エントリに複数の hook を並べると上から順に評価され、先の hook が block した時点で後続には到達しない。

対象パスが入れ子になる hook を足す時にこれが効いてくる。

"matcher": "Write|Edit|MultiEdit",
"hooks": [
  { "command": "... enforce-ssot-record.sh" },   // 対象: 01_DECISIONS/ 配下すべて
  { "command": "... guard-config-secrets.sh" }   // 対象: 01_DECISIONS/claude-code/設定ファイル/
]

後者の対象は前者の対象に完全に含まれるため、前者がブロックする条件下では後者は一度も走らない。

フラグ無し → enforce が block(exit 2) → guard-config-secrets に到達しない
フラグ有り → enforce は通す        → guard-config-secrets が検査する
  • 設計としては筋が通る: 後段は「スキル経由なら何でも書ける」という前段の抜け穴を塞ぐ位置にいる
  • テスト設計に影響する: 後段を検証したいなら、前段を通過する状態を作ってからテストする （上の例なら ~/.claude/state/ssot-record-active-* を置いてから）
  • 順序を意識せずに足すと「登録したのに一度も走らない hook」が生まれる

PreToolUseでブロックする時は exit 2 ではなく JSON を返す（2026-08-22）

Windows Desktop 版では exit 2 が効かない。stdout に以下を出して exit 0 で終えること。

printf '{"decision": "block", "reason": "..."}\n'
exit 0

exit 2 を併記すると stdout の JSON 側が無視されるため、併用しない。 check-command-safety.py がこの方式で実際に動作している唯一の実証例。

テストの合格基準を exit code にしていると、テストは緑なのに実環境では無防備という 状態を見逃す。判定は「実際にブロックされる出力が出るか」で書くこと。

hook が本当に発火したかを実測する（2026-08-23）

設定が正しいことと、実際に発火していることは別。1コマンドで両方を分けて測る:

wsl bash -lc "bash ~/bin/verify-hook-matchers.sh --session-id $CLAUDE_CODE_SESSION_ID"

終了コードは 0=PASS / 1=FAIL / 2=SKIP（判定不能） の3値。

--session-id を必ず渡すこと。 CLAUDE_CODE_SESSION_ID は Claude Code を動かしている Windows 側シェルにしか無く、wsl bash -lc の内側へは伝播しない（実測）。 渡さないと「自セッションを特定できない」として SKIP になる。

⚠️ 他セッションの記録で「発火している」と判断してはいけない。 ~/.claude/logs/tool-usage-YYYY-MM-DD.csv には並行セッション全部の記録が混ざる （2026-08-23 実測で1日7セッション・119件）。session_id で絞らずに件数だけ見ると、 自分の hook が死んでいても他人の記録で PASS に見える。2026-08-22 に実際にこれで誤判定した。

SKIP は「異常なし」ではない。判定材料が無いという意味なので、理由を読んで対処する:

SKIP の理由 対処
自 session_id を特定できない --session-id を渡す
自セッションの記録が本日0件 ツールを1回使ってから再実行（PostToolUse がまだ完了していないレース）
WSL⇔Windows の時計がずれている sudo hwclock -s で合わせてから再実行

概要

GitHub Issue を順番に自動実装するイベント駆動ループ。
CronCreate が時間トリガーのみなのに対し、Stop Hook を使うことで「前のタスク完了後に次を起動」が実現できる。

ファイル構成

~/.claude/scripts/auto-dev/
├── state.json       # キュー状態（永続）
├── start.sh         # 手動起動エントリポイント
├── next-issue.py    # Stop Hook 本体
└── loop.log         # 実行ログ（自動生成）

使い方

# WSL で実行（Issue #76 → #75 の順で自律実行）
bash ~/.claude/scripts/auto-dev/start.sh 76 75

# 状態確認
cat ~/.claude/scripts/auto-dev/state.json

# ログ確認
tail -f ~/.claude/scripts/auto-dev/loop.log

緊急停止

python3 -c "
import json
p='/home/<USER>/.claude/scripts/auto-dev/state.json'
s=json.load(open(p))
s['active']=False
json.dump(s,open(p,'w'),indent=2)
print('停止しました')
"

誤爆防止

  • state.active == false の時は next-issue.py が即 exit(0) — 通常の会話終了では何も起きない
  • except 節で必ず exit(0) — Stop Hook がセッション終了をブロックすることはない

start.sh 76 75
  → state.json: active=true / pending=[76,75]
  → claude --print "Issue #76 を実装して..."
  → [セッション終了]
  → Stop Hook → next-issue.py
      → completed=[76] / pending=[75]
      → claude --print "Issue #75 を実装して..."
      → [セッション終了]
  → Stop Hook → next-issue.py
      → completed=[76,75] / pending=[] → active=false → 完了

PreToolUseでのコマンド書き換え（updatedInputパターン）

PreToolUseフックはブロック（{"decision": "block", ...}）だけでなく、ツールの実行直前にその入力を書き換えることもできる。以下のJSONをexit code 0で標準出力プログラムが結果を書き出す標準的な出口。画面表示や次のプログラムへの受け渡しに使われる。ちなみにエラー情報は「標準エラー出力」という別の出口に出るに書くと、updatedInputで指定した内容が実際の実行に反映される（セッション再起動不要・live反映）。

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "updatedInput": { "command": "書き換え後のコマンド文字列" }
  }
}

実例（Windows Desktop版限定）: path-rewrite.pyは、Bashコマンド文字列内の既知WSLホームパスプレフィックス（~/projects/・~/.claude/・/home/<USER>/projects/・/home/<USER>/.claude/の4種のみ＝ホワイトリスト）をUNCパス（//wsl.localhost/Ubuntu/home/<USER>/...）に単純文字列置換する。これにより、WSL CLI版で書かれた共有ファイル（handoff/SKILL.md/SSOT）内のパスをWindows Desktop版でも変換なしで実行できる。

注意点（実機検証で判明）: ①wsl bash -c "..."でラップしたコマンド内のパスも書き換えの対象になるため、ホワイトリスト導入後は対象パスをwsl bash -cでラップする必要自体がなくなる（直接実行すればよい）。②既にUNC形式で手書きしたパスは部分文字列としてホワイトリストに再マッチし二重化することがあるため、UNCパスは手書きせず~/projects/...等の表記に統一する。詳細: 2026-06-30_Windows-Desktop版WSLパス変換フック実装
