24 スマホからのリモート操作 — 外出先から自宅の Claude Code を触る構成

スマホから自宅 PC の Claude Code を安全に操作する環境を、公式機能の制約を実測して bypass した記録。モバイル回線に切り替えてもセッションClaude Codeの1回の対話単位。起動から終了までの会話と作業状態のこと。長く使うと内容が混ざるため、トピックの区切りで新セッションに引き継ぐ運用をするが死なない mosh 構成までの手順。

はじめに

「移動中や外出先から、自宅 PC の Claude Code に指示を出したい」——そう考えたとき、公式には Remote Control という機能があります。しかし プロキシ通信の中継役。「クライアント→プロキシ→本来の宛先」の順に通信を一度経由させる仕組みで、仲介者が経路の切替・集計・制限等を担当するや gateway 経由で Claude Code を動かしている環境では使えない という制約があり、実際に試すと:

/remote-control
→ Remote Control is not available for this deployment.

とはいえ諦める必要はありません。Tailscale + SSH + tmux の上に mosh を重ねるだけで、公式機能に近い体験を自前で構築できます。この章は、その実際の手順と「なぜそうなるか」を順に説明します。

全体構成

スマホ（Moshi アプリ）
   │  mosh（切れても自動再接続の UDP 通信）
   ▼
Tailscale 仮想ネットワーク（端末同士の専用通路）
   ▼
自宅 PC の WSL2（sshd :22）
   ▼
tmux セッション（ここに Claude Code が常駐）

ポイントは モデル通信（APIApplication Programming Interface（エーピーアイ）の略。あるプログラムの機能を、別のプログラムから呼び出せるようにした「窓口」 呼び出し）は自宅 PC 側の設定のまま という点です。スマホはあくまで「画面とキーボードの受け窓」なので、プロキシ環境でも deployment 制約を受けません。

手順 1: 土台の確認（Tailscale・SSH・tmux）

すでに Tailscale + SSH + tmux で自宅 PC に入れる人は、この手順は読み飛ばして構いません。

  1. PC とスマホ両方に Tailscale を導入して同じアカウントにログインする。PC 側の Tailscale IP（100.x.y.z 形式のプライベート IP）を控えておく
  2. WSL2 内で sshd を起動する（sudo apt install -y openssh-server → sudo service ssh start）
  3. tmux を導入（sudo apt install -y tmux）

手順 2: mosh の導入

mosh（Mobile Shell）は「一度切れても自動で繋ぎ直る」通信方式です。WiFi からモバイル回線への切り替えや、圏外からの復帰でもセッションが生き続けます。素の SSH は TCP 接続なので、一度切れるとやり直しです。

sudo apt install -y mosh
# 動作確認（一時的に起動して UDP ポートで待ち受けるか見る）
mosh-server new -v
# → MOSH CONNECT 60001 ... と出れば成功

手順 3: スマホアプリ（Moshi）の設定

モバイル側は Moshi（getmoshi.app・iOS/Android）を使います。AI コーディングエージェント与えられた目標に向かって、自分で手順を組み立てて作業を進めるAIプログラム。質問に答えるだけのチャットAIと違い、「調べる→書く→確認する」を自律的に行うの遠隔操作に特化した SSH/Mosh クライアントです。ホスト設定は以下のとおり:

項目 値
Address Tailscale で控えた PC の IP（100.x.y.z）
Port 22
Username WSL のユーザー名
認証「あなたは誰か」を確認すること。パスワードや鍵で本人であることを確かめる手続き WSL のパスワード
接続方式 Mosh
Mosh のパス /usr/bin/mosh-server（任意だが指定すると確実）
起動コマンドターミナルに入力してコンピュータに与える一行の指示。lsやcdのように『プログラム名+補足指定』で構成される tmux new -A -s claude

tmux new -A -s claude は「claude という名前のセッションがあればそこに接続、無ければ作る」の意味です。これを起動コマンドにしておけば、接続ボタンを押すだけでいつでも同じ作業部屋に戻れます。

なぜ mosh なのか（SSH との比較）

SSH mosh
ネットワーク切替時 切れて終わり 自動で繋ぎ直る
入力の反映 回線が遅いとカクつく ローカルエコーで打った瞬間に表示
セッションの寿命 接続と命運を共にする 接続と独立（tmux と併用で二重の保険）
必要なもの なし（標準） ホスト側に mosh-server

モバイル運用では「切れなさ」がすべてなので、mosh 一択です。ただし UDP が塞がれたネットワークでは繋がらない ことがあるため、同じアプリ内で接続方式を SSH に切り替えられる予備ホストを 1 つ作っておくと安心です。

運用の知見（実測で得た注意点）

⚠ PC のスリープには勝てません。mosh は「通信の切れ」に強いだけで、PC 自体がスリープすると WSL ごと停止します。外出先で繋がらないときの切り分けは、①スマホの Tailscale スイッチ ②PC がスリープしていないか、の順で。

⚠ 公式 Remote Control は認証方式に制約があります。API キー認証や gateway/プロキシ経由（ANTHROPIC_BASE_URL を api.anthropic.com 以外に向けている構成）では利用できません。エラーが出たら「機能が廃止された」ではなく「自分の認証モードが対象外」と疑うのが近道です。

💡 接続方式の選択肢。Moshi には SSH / Mosh / ET（Eternal Terminal・実験的）の選択肢があります。SSH は予備、ET はホスト側に別ソフトが必要なため、まずは Mosh + SSH 予備の 2 段構成で十分です。

まとめ

  • 公式機能に制約があっても、Tailscale + mosh + tmux の組み合わせで自前構築できる
  • モデル通信は自宅 PC 側のままなので、プロキシ/gateway 環境でも制約を受けない
  • 「切れない」は mosh と tmux の二重構造で担保する（通信と作業の両面）
  • スリープは越えられない壁——外出先で繋がらないときはまず PC の状態を疑う

方法2: OpenMausBot（チャットUI型・2026-11-17追加実測）

GitHub人気OSS OpenMausBot（24.1k★）を使うと、「ターミナル文字だけでパソコンと対話する画面。コマンドを打ち込むと結果が文字で返ってくる。Claude Code CLIはここで動くを握る」代わりに「チャット画面からAIエージェントに頼む」形で自宅の Claude Code を操作できます。自分のマシンにインストール済みの CLI（claude / codex / grok）を自分のログイン・サブスクリプションのままエンジンとして登録する思想（bring-your-own-agent）で、プロキシ環境でも制約を受けません。

Moshi構成との違い: Moshi は「ターミナルの画面を遠隔で握る」ので操作は人間。OpenMausBot はチャットで頼むとエージェントが動く。承認カード（Allow/Deny）がチャット内に出る点は CC の permission モデルと同じです。

全体構成（実測）

スマホ/ブラウザ（OpenMausBot専用アプリ or Webアプリ）
   │  ペアリングHTTPS（--tailscale / --tunnel 対応）
   ▼
Windows側 OpenMausBot（Electron・ハーネス 127.0.0.1:8799）
   │  ACP over stdio（customAcp ドライバー）
   ▼
wsl.exe -e ~/bin/claude-code-acp-wsl.sh（ラッパー）
   │  ①nvm PATH補正 ②--version対応 ③cwd Windows→/mnt/c 変換
   ▼
WSL内 claude-code-acp 0.16.2 → Claude Code SDK → claude CLI
   │  ~/.claude/settings.json（ANTHROPIC_BASE_URL=glm-rate-proxy）
   ▼
glm-rate-proxy(localhost:8787) → ZAI GLM

導入手順（実測・WSL2 + プロキシ環境）

  1. Windowsにインストール: GitHub Releases（milind-soni/openmausbot-releases）から OpenMausBot-setup.exe（約258MB）。⚠ Windows版は未署名（macOSのみ署名済み）・SmartScreen警告が出たら詳細情報→実行
  2. WSL内にACPアダプタ: npm install -g @zed-industries/claude-code-acp（Claude Code SDKベース・nvm環境なら通常PATHでは見えないので次のラッパー必須）
  3. ラッパー作成 ~/bin/claude-code-acp-wsl.sh（chmod +x 忘れずに）:
#!/bin/bash
export PATH="/home/<user>/.nvm/versions/node/v<ver>/bin:$PATH"
if [ "$1" = "--version" ]; then echo "claude-code-acp 0.16.2"; exit 0; fi
python3 -u -c '
import sys, re
pat = re.compile(r"\"cwd\"\s*:\s*\"(C:[^\"]+)\"")
for line in sys.stdin:
    out = line
    m = pat.search(line)
    if m:
        w = m.group(1)
        u = "/mnt/c" + w[2:].replace("\\\\", "/")
        out = line.replace(m.group(0), "\"cwd\":\"" + u + "\"")
    sys.stdout.write(out)
    sys.stdout.flush()
' | claude-code-acp "$@" 2>> ~/.cache/claude-code-acp-wsl.log
  1. エンジン登録: C:\Users\<user>\.openmausbot\config.json に追記（アプリ再起動で読み込まれる）:
{
  "instances": {
    "claude-wsl": {
      "driver": "customAcp",
      "displayName": "Claude (WSL)",
      "environment": {},
      "config": { "cli": "wsl.exe -e /home/<user>/bin/claude-code-acp-wsl.sh" }
    }
  }
}
  1. 設定画面でセットアップ: 歯車 → AI → 「その他のプロバイダー」→ Claude (WSL) → セットアップ。緑ドット「準備完了」になればOK

落とし穴3件（実測）

症状 原因 解決
「version check timed out after 8 seconds」 claude-code-acp本体は--versionで空出力して終了する（文字列を出さない） ラッパーでバージョンソフトウェアやファイルの「どの時点の状態か」を示す番号。v1.2等。更新のたびに番号が上がる文字列を出力してexit 0
テスト時に「cannot be launched inside another Claude Code session」 CCセッションの子プロセス動いているプログラム1つ1つの実体。番号（PID）で管理されるはCLAUDECODE環境変数プログラムの外側（OS側）で設定する値の入れ物。プログラムを書き換えずに設定を切り替えられる。APIキー等の秘密の値はソースコードに直書きせずここに入れるのが安全な定石を持つ（ネスト検知） テスト時はenv -u CLAUDECODE・実機（アプリ経由）は非該当
「Query closed before response received (session/new)」 アプリはsession/newに cwd: C:\Users\...（Windowsパス） を渡し、WSL内アダプタが即死 ラッパーにstdin中継で /mnt/c/ 変換を実装設計や仕様を、実際に動くコードに作り込むこと。「実装済み」＝コードとして完成している状態

変換実装の注意: "C:\\Users"（JSONジェイソン。データを記述する標準的な書式の1つ。設定ファイルやデータのやり取りに広く使われ、「名前: 値」の組み合わせで書くエスケープ特別な意味を持つ文字（< > 等）を、ただの文字として扱われるよう別の書き方に変えること。画面表示や注入攻撃の防止に使う2バイト）を w[3:] で切ると C: 後の2バイトのうち1個を切り捨ててJSON壊れ。w[2:] + prefix /mnt/c が正解（バイトレベルで単体テスト関数など部品単位で動作を確認するテスト。pytestはPythonの定番テスト実行道具。変更のたびに自動で回して壊れていないことを担保する推奨）。

スマホとの繋ぎ方（実測・2026-11-18・Galaxy Z Flip7で往復完遂）

  • ⚠ 最初に知るべき制約（実測）: デスクトップアプリで起動中のサーバーは、CLIの openmausbot pair が拒否される（「The OpenMausBot desktop app runs this server, so it only pairs devices from the app itself」）。アプリUIの Settings → Phone & devices からペアリングするか、CLIでペアリングするなら独立サーバー方式を使う
  • ⚠ ポート同じPCの中で複数のプログラムが通信を待ち受けるための「窓口番号」。8787番・3000番のように番号で区別する注意（実測）: デスクトップアプリは 8799 に加え 8800 もlistenしている。独立サーバーは 8880台の空きポートを選ぶ（実測では8888）

独立サーバー方式の手順（実測・engine設定引き継ぎ込み）:

  1. engine設定をコピー: 既存 C:\Users\<user>\.openmausbot\config.json の instances（例: claude-wsl）を新しいdata-dirへコピー（例: C:\Users\<user>\.openmausbot-mobile\config.json・instances と onboarding の2キーでOK）
  2. 起動: npx openmausbot serve --port 8888 --data-dir C:\Users\<user>\.openmausbot-mobile --tailscale --no-open → Reach http://<machine>.<tailnet>.ts.net:8888 ✓ answers as this server と出ればOK
  3. Tailscale HTTPエイチティーティーピー。Webの通信で使われる基本的な約束事（プロトコル）。ブラウザとサーバー、プログラム同士のやり取りの共通言語S証明書が使えないアカウントでも動く: your Tailscale account does not support getting TLS certs が出ても、サーバーは http://<machine>.<tailnet>.ts.net:8888 でlistenし、tailnet限定+WireGuard暗号化で実用になる（公式docsもこの挙動を明記）
  4. ペアコード発行: npx openmausbot pair --port 8888 --data-dir <dir> --public-url http://<machine>.<tailnet>.ts.net:8888 --ttl 24h → 12桁コード+リンク+QRが出力される（コードは1回限り・検証等で消費したら再発行）
  5. スマホで開く: リンク（/pair#code=<12桁>）をスマホのChromeで開くとコードが自動処理されてペアリング完了 →「Open the app」でチャット画面 → Chromeメニュー「インストール/ホーム画面に追加」でPWA化
  6. 複数デバイス: openmausbot devices で一覧・devices revoke <id> で個別失効。機数分の並列複数の処理を同時に進めること。順番に1つずつやる「直列」の対義語ペアリング可（各機にTailscale参加+都度コード発行が必要）

実測結果（2026-11-18）: Galaxy Z Flip7 とペアリング → スマホUIからメッセージ送信 → WSL内CC（GLM）の応答が返る往復を、スマホのスクショとAPIポーリングの両方で確認。スマホ側はadbワイヤレスデバッグ不具合の原因を特定して直すこと。ログや実行の跡を辿って、どこで期待と違う動きをしたかを突き止める作業（adb pair <IP>:<port> <6桁> → adb connect → screencap -d <display-id> -p）でCCから自動検証まで可能（⚠ Z7のような2ディスプレイ構成は screencap に -d <display-id> 指定が必須・未指定だとPNGでなく警告テキストが返る）

常時化（PC再起動後も自動起動・実測2026-11-18）

  • openmausbot service install は Windows 非対応（CLI help実測・v0.1.169時点: "writes a systemd unit (Linux) or a launchd agent (macOS)"）。Windowsでの恒久化は下記のスタートアップ方式を使う
  • 生存挙動の実測: バックグラウンド実行（CCセッションのbackgroundタスク等）で起動した serve は、そのセッション/タブを閉じても生存する（Windows側でプロセスが切り離されて動くため）— 真に消えるのは PC再起動・ログオフ時。ターミナルのウィンドウ自体を閉じた場合は停止する

スタートアップ方式の手順（実測・管理者権限不要）:

  1. バージョン固定インストール: Windows側で npm i -g openmausbot@0.1.165（npxキャッシュ一度得た結果を取っておいて、次回は同じ計算をせず使い回す仕組み。速くなるが、元のデータが変わった時の更新忘れに注意依存を断つ・テザリング直後の不安定なネットワークでも起動できる）
  2. 起動スクリプト自動実行できる小さなプログラム。手順を書いたテキストファイルの形をしている openmausbot-serve.cmd（C:\Users<user>\ 直下）: ①tailscale待ち（最大3分・tailscale status ポーリング）②ポート8888の二重起動ガード（netstat | findstr・占有時に所有PIDをログ出力）③openmausbot serve ... 起動（ログは openmausbot-serve.log へ追記・5MBでローテ）④異常終了時は30秒待って再起動（連続10回で自動停止・手動再起動案内をログ出力）。⚠ バッチで if (...) ブロック複数の処理が同時に同じ対象を触って衝突するのを防ぐ「鍵」の仕組み。鍵を持っている間は他の処理は待つか諦める内のechoにASCIContinuous Integration（シーアイ・継続的インテグレーション）の略。コードを変更するたびに自動でテストとチェックを回し、壊れていないかを常に確認する仕組みI括弧を書くとブロックの閉じ括弧と衝突して即死する（隠し窓だと無音で気付けない）→ goto 構造で書くのが安全
  3. 非表示ランチャー openmausbot-serve-launcher.vbs: CreateObject("WScript.Shell").Run """...serve.cmd""", 0, False — ログオン時にコンソール窓を出さないための皮
  4. スタートアップ登録: Win+R → shell:startup フォルダに launcher.vbs へのショートカット（.lnk）を置く
  5. 再ペア用ショートカット OpenMausBot再ペア.cmd（デスクトップ）: ネット切替等でブラウザ側のペア鍵が失効した時、openmausbot pair のコード発行+URL表示を1クリックで行う（⚠ cmdに日本語を書く場合はCP932保存・UTF-8だと文字化け）

ネット切替（Wi-Fi↔テザリング）の挙動（実測）: サーバープロセスはネットワーク切替の影響を受けない（ローカルlisten・Tailscale経由の到達はtailscaleが自動再接続・数秒〜数十秒）。ただしブラウザ側のペア鍵は切替で失効する機種がある（Chromeのタブ破棄が疑い・実測で機差: 生存する機種と失効する機種があった）→ 再ペア.cmdで復旧。スマホ側は**PWA化（ホーム画面に追加）**しておくとタブ破棄されにくく失効が減る見込み。サーバー側のペアエントリは切替で消えない（30日有効・data-dirのsessions.jsonに永続）

成功確認の方法（実測済み）

  1. プロキシログに agent-sdk UA のリクエストが記録される: journalctl --user -u glm-rate-proxy | grep agent-sdk → POST /v1/messages 200 + Captured actual model (SSE): glm-5.3-flash
  2. チャットの応答にCCの設定が反映される（バッジ表示ルール等）
  3. 設定 → AI → Claude (WSL) が緑ドット「準備完了」

注意点

  • OpenMausBotのツール群（チーム・ブラウザ・PC操作）はWSL内エンジンからは使えない（アプリUI明示の警告）— チャット応答のみ・「自宅のCCに話しかける」用途
  • 企業サインインは個人環境ではエラー（Admin portalアドレス設定が無い）— ローカル利用はサインイン不要で動く
  • Windows版インストーラは未署名（v0.1.165時点）
