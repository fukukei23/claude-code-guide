# 05 フック — イベント駆動の自動実行

> 💡 **章の核**: hookは「LLMの約束」を機械が強制する唯一の層。事故を止めたいならここに実装する。


## フックとは

フックは **特定のイベント発生時に自動実行されるシェルスクリプト**。Claude Codeの動作を拡張・制御する。

```
ユーザーがツールを実行
  │
  ▼
PreToolUse フックが発火 ──→ チェックOK → ツール実行
  │                          └─ チェックNG → ブロック
  ▼
ツールが実行される
  │
  ▼
PostToolUse フックが発火 ──→ ログ記録・後処理
```

---

## 主要4種のフック

### <a id="sessionstart"></a>SessionStart

**セッション開始時**に実行。

| 項目 | 説明 |
|---|---|
| タイミング | Claude Code起動時 |
| 用途 | 環境変数の読み込み、初期化処理、設定の検証、ハンドオフ読込 |
| あなたの設定 | `~/.secrets.env` からAPIキーを注入、MCP設定の自動チェック、スキルトリガーマップ自動表示、SSOT日記読込 |

### <a id="pretooluse"></a>PreToolUse

**ツール実行前**に実行。最も重要なフック。

| 項目 | 説明 |
|---|---|
| タイミング | 各ツール（Read, Edit, Bash等）の実行前 |
| 用途 | セキュリティチェック、危険コマンドのブロック、入力検証 |
| あなたの設定 | `check-command-safety.py` が危険コマンドを自動ブロック・`check-review-policy-gate.sh` がclaude-configのcommit時にreview_policy.yaml直書きを検査（.githooks/pre-commit・SKIP_GREP=1で緊急スキップ）・`git-commit-diff-check.sh` がgit commitのstage行数検査(±10warn/±20block・観測ロガー flock+\|\|true fallback+1MB rotation・宣言エンジン分類後block=L279修正2026-09-04: status A新規はblock対象外・`git commit -- <paths>` は指定パスのみ判定・自タブpaths.json宣言内とstale宣言はwarnのみ通過・**C′=ボード✅行ベース格下げ（2026-09-07・shadow既定）**: ボードに✅行のみのタブ（🟢行が残る再開タブは対象外）の宣言をOTHER_DONE分離し、shadow=block継続+`blocked-commits.jsonl`構造化ログ、`PATHS_CPRIME_MODE=enforce`でstale格下げ（warn only）・パース不能時は`cprime_fallback`記録+現行挙動維持（保守側）） |
| ブロック可能 | **Yes** — スクリプトがエラーを返すとツール実行がキャンセルされる |

> 💡 ※2026-07-02統合撤去: 2026-06-30に追加していた minimax系MCPブロック（matcher `mcp__minimax-(official|video)__.*`・`exit 2`）は、32MB真因=glm-rate-proxy `client_max_size` 未設定と判明（9ac5f24fd解決）したため PreToolUse hook を削除し撤去。minimax-official/video は日常セッションで即呼び可能。

> **現場の知見**: フックのスクリプトがエラー（exit code ≠ 0）を返すと、ツールの実行がサイレントにブロックされる。意図せぬブロックに注意。→ [11_現場の知見](12_現場の知見.md#b-落とし穴ハマりポイント)

> **クロスプラットフォーム対応**: フックスクリプトで `python3` を直接呼ぶとWindows Git Bashで動作しない。`run-security-check.sh` ラッパーが python3 / python / wsl を自動検出する。Bashフックは純bash（grep/sed）でJSON解析しpython3に依存しない。

ブロックされるコマンドの例:
- `bash -x`（デバッグ出力でシークレット露出の恐れ）
- `cat -A`（特殊文字表示でシークレット露出の恐れ）
- マスクなしの `grep`（APIキーを含むファイルの検索）
- フィルタなしの `env`（全環境変数の表示）

### <a id="posttooluse"></a>PostToolUse

**ツール実行後**に実行。

| 項目 | 説明 |
|---|---|
| タイミング | 各ツールの実行後 |
| 用途 | ログ記録、実行結果の後処理、設定の自動同期、通知 |
| あなたの設定 | ツール使用ログ記録、commit検知（SSOT記録トリガー）、settings.jsonの自動同期、スキル変更のmirror、**guard-settings-write**（Task6 α C'案・settings.json への TOKEN 書込を内容ベース差分検知で防御・✅実装済 2026-07-31・2026-08-01 層2.5 Shannon entropy追加でhex/base64-only TOKEN捕捉・test 80/80・2026-08-12 H恒久対策: クォート付きURL正規化(split_inner_args)で偽陽性ループ解消・test 85/85）・**declare-playwright-use**（2026-10-10新設・matcher `^mcp__plugin_playwright_playwright__browser_`で限定・Playwright使用を宣言jsonに自動記録＝宣言忘れを構造的に消す・`pw-declare-wrap.sh` timeoutラッパ経由でguard誤爆回避） |・**proxy-op-gate**（2026-10-20新設・matcher Bash・プロキシ操作コマンド6パターン検知→paths.json宣言+one-shotトークン→ask/pass・flock排他・ledger=~/.claude/state/proxy-op-gate/ledger.jsonl）・**proxy-op-confirm**（2026-10-20新設・PostToolUse Bash・ask承認を経た実行をledgerにconfirmed記録）

### <a id="stop"></a>Stop

**セッション終了時**に実行。

| 項目 | 説明 |
|---|---|
| タイミング | Claude Code終了時 |
| 用途 | クリーンアップ、ログ保存、ハンドオフ情報の書き出し |
| あなたの設定 | セッション終了時のサマリー記録、ガイド更新キューの記録、設定の最終同期、**glm-5.3戻し忘れ検知（`check-model-stay.sh`・全タブ合算で継続30分超+5ターン超を検知しCCへ警告+Windowsトースト・判定ロジックは`model_stay_detector.py`共有・効果測定ログ`model5-3-warn-log.jsonl`）**・**playwright-occupancy-gate**（2026-10-10新設・宣言あり+自lock残存で差戻し「browser_close呼べ」・上限3回・skip6種・`pw-gate-wrap.sh` timeoutラッパ経由） |

### Notification / PostToolUseFailure

エラー・ブロック時（Notification）、ツール失敗時（PostToolUseFailure）に実行。Discord通知等の異常系ハンドリングに使用。

### PermissionRequest（承認要求時）

承認プロンプトが出た瞬間に実行（2026-09-29配線・`notify-windows-approval.sh`）。Windows側でbeep2回+MessageBoxを出す通知専用hook（async fire-and-forget）。実発火E2E済み（ask ルールでPermissionRequestを発生させて音/ポップアップを人間観測）。

> ⚠️ **settings.jsonに書くhookコマンドは `~` 形式digit-freeに限定すること**（2026-09-29実測）: guard-settings-write の層2（長文字列32字+文字種3種=TOKEN様判定）が、`/home/yn4416`（数字入り絶対パス）や `exit 2`（数字）を含むコマンド文字列をTOKENと誤判定して**復元**する。`~/.claude/...` 形式（小文字+記号のみ=文字種2種）ならCLEAN通過。数字が必要な処理（exit 2への変換等）はラッパスクリプト側に分離する（実例: `run-vision-pack-gate.sh`）。詳細: [[01_DECISIONS/claude-code/2026-09-29_通知と視角パックhook配線完了-guard層2誤検知原因特定.md]]

## 設定方法

フックは `settings.json` の `hooks` セクションに定義する。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ~/.claude/scripts/security/check-command-safety.py"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "source ~/.secrets.env"
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/scripts/session/save-session-log.sh",
            "timeout": 5000
          },
          {
            "type": "command",
            "command": "~/.claude/scripts/session/generate-handoff.sh",
            "timeout": 3000
          },
          {
            "type": "command",
            "command": "~/.claude/scripts/session/queue-guide-updates.sh",
            "timeout": 5000
          }
        ]
      }
    ]
  }
}
```

### matcherについて

- `matcher` はツール名を指定（例: `"Bash"`, `"Edit"`, `"Read"`）
- 空文字 `""` は全ツールにマッチ
- 複数のフックを設定可能（配列で定義）

### 🚨 Windows Desktop版では `wsl bash -c "..."` 形式で書くこと（2026-08-22・最重要）

Windows Desktop 版の settings.json に hook を書く時、コマンドを **`wsl bash <posixパス>` 形式にしてはいけない**。

```jsonc
// ❌ 動かない（エラーも出ずに何もしない）
"command": "wsl bash /home/yn4416/.claude/scripts/hooks/track-tool-usage.sh"

// ✅ 動く
"command": "wsl bash -c \"bash /home/yn4416/.claude/scripts/hooks/track-tool-usage.sh\""
```

**理由**: Windows 側から `wsl bash /home/...` を起動すると、MSYS のパス変換で
`/home/yn4416/...` が `C:/Users/yn441/...` に書き換えられ、WSL 内でファイルが見つからず
**無言で失敗**する。`-c "..."` で括ると変換を免れる。

```
$ printf '…' | wsl bash /tmp/guard_copy.sh
bash: C:/Users/yn441/AppData/Local/Temp/guard_copy.sh: No such file or directory
```

2026-08-22 時点で **27 hook 中 25 本がこれに該当**し、破壊的コマンドのブロック層を含めて
全滅していた。動いていた2本はいずれも `wsl bash -c "python3 ..."` 形式だった。

> ⚠️ **matcher のせいだと誤診しやすい**。「特定の matcher の hook だけ動く」という症状が出るが、
> 実際は matcher ではなく**その hook がたまたま `-c` 形式で書かれていた**だけ、ということがある。
> 2セッションにわたり `matcher:""` → `matcher:"*"` と是正を繰り返して効果が出なかった事例あり。

**切り分け手順**: 「機能が無反応」に見えたら、スクリプトを疑う前に **hook が呼ばれているか**を先に見る。
スクリプト冒頭に `date >> /tmp/canary.log` を一時挿入し、ツールを1回使ってファイルができるか確認する。
できなければ原因は呼び出し側（＝この項目）にある。

### 「何も起きない＝正常」の hook は fail 条件側で測る（2026-08-30）

`git-commit-diff-check.sh` のように**異常時だけログを書く** hook は、正常系をいくら流してもログが増えない。
「ログ行数が増えれば PASS」という検証は、**hook が完全に死んでいても完全に動いていても同じ結果**になりうる。

2026-08-30 の実例: 「50行のファイルを stage して commit → ログが増えれば PASS」という手順を作ったが、
`T=/tmp/x; cd $T` と**変数**を使っていたため hook 側の対象repo解決（`cd <path> && git commit` の
リテラル解析・スクリプト53〜56行目）が失敗し、clean な CC の cwd を検査して無言で終了していた。
**PASS し得ない手順**だった。

- 対象repoを跨ぐ検証では **`cd /literal/path && git commit`** とリテラルで書く
- 判定は「ログが増えたか」ではなく **「ブロックされたか（コマンドが実際に止まったか）」** で書く
- 正しく測れた時の出力例:
  ```

  EXIT_CODE=2
  REASON=stage変動が1ファイル±20行超を検出: fire5.md (max delta=50)
  ```

**判定の直前でパス区切りを正規化**すること。Windows Desktop 版は次の形で渡してくる。

```
\\wsl.localhost\Ubuntu\home\yn4416\projects\obsidian-ssot\01_DECISIONS\claude-code\x.md
```

```bash
# ❌ 素通りする（"01_DECISIONS\claude-code" なので一致しない）
case "$FILE_PATH" in *01_DECISIONS/*) ... ;; esac

# ✅ 判定の直前で正規化
FILE_PATH=$(printf '%s' "$FILE_PATH" | tr '\\' '/')
case "$FILE_PATH" in *01_DECISIONS/*) ... ;; esac
```

```python
# python 側で判定する場合
fp = (ti.get("file_path", "") or "").replace("\\", "/")
```

> ⚠️ **`path-rewrite.py` があっても直らない**。あれは `tool_input.command`（Bash のコマンド文字列）が
> 対象で、**`tool_input.file_path` は別経路**なので変換されない。「Bash の hook は効くのに
> Write/Edit の hook だけ効かない」という症状は、matcher ではなく**この経路差**が原因のことがある。

2026-08-30 時点で3つの hook がこれで素通りしていた（`enforce-ssot-record.sh`・
`guard-config-secrets.sh`・`warn-naming-rules.sh`）。うち `guard-config-secrets.sh` は
**設定ファイルへの生シークレット混入を止める層**だったため、実害の大きい抜けだった。

**切り分けの決め手**: 「matcher が効かない」と「判定が一致しない」は症状が同じに見える。
**同じスクリプトに区切り違いの file_path だけを流して比較**すると1回で確定する。

```
A: /home/.../01_DECISIONS/claude-code/x.md          → exit 2（ブロックされる）
B: \\wsl.localhost\...\01_DECISIONS\claude-code\x.md → exit 0（素通り）← 差は区切りだけ
```

### 同一エントリ内の hook は順に評価される — 対象が入れ子なら前段の通過条件に注意（2026-08-30）

1つの matcher エントリに複数の hook を並べると**上から順に評価**され、**先の hook が block した時点で後続には到達しない**。

対象パスが**入れ子**になる hook を足す時にこれが効いてくる。

```jsonc
"matcher": "Write|Edit|MultiEdit",
"hooks": [
  { "command": "... enforce-ssot-record.sh" },   // 対象: 01_DECISIONS/ 配下すべて
  { "command": "... guard-config-secrets.sh" }   // 対象: 01_DECISIONS/claude-code/設定ファイル/
]
```

後者の対象は前者の対象に**完全に含まれる**ため、前者がブロックする条件下では後者は一度も走らない。

```
フラグ無し → enforce が block(exit 2) → guard-config-secrets に到達しない
フラグ有り → enforce は通す        → guard-config-secrets が検査する
```

- **設計としては筋が通る**: 後段は「スキル経由なら何でも書ける」という前段の抜け穴を塞ぐ位置にいる
- **テスト設計に影響する**: 後段を検証したいなら、**前段を通過する状態を作ってからテストする**
  （上の例なら `~/.claude/state/ssot-record-active-*` を置いてから）
- 順序を意識せずに足すと「登録したのに一度も走らない hook」が生まれる

### ssot-record強制ゲートは「フラグ+marker」の二重制（2026-09-07・L74-M1）

`enforce-ssot-record.sh` は 01_DECISIONS/ と 00_SYSTEMハブ対象への Write/Edit に対し2つの証を要求する:

1. **フラグ** `~/.claude/state/ssot-record-active-<SID>` — ssot-record スキルがフェーズ3で作成（従来どおり）
2. **marker** `~/.claude/state/ssot-record-mapping-run-<SID>` — **A層スクリプト `ssot-record-detect-targets.py` がフェーズ0.5で発行**（マッピング2ファイル読込の実行証跡）

- marker が無い・TTL（6h）切れ・**stale（マッピング更新後にmtime/sha256照合で検知）**の場合は block され「A層スクリプトを再実行」と表示される
- **回復は再実行のみ**。marker の手動作成（touch等）は禁止（スキル本文契約）
- SID（照合キー）は **hook入力stdin JSONの `session_id`** から取得（2026-09-10 E案・env変数 `CLAUDE_CODE_SESSION_ID` は参照しない単一経路）。stdin未取得・不一致は fail-closed 全面block（緩和フォールバック不導入）

### PreToolUseでブロックする時は `exit 2` ではなく JSON を返す（2026-08-22）

Windows Desktop 版では **`exit 2` が効かない**。stdout に以下を出して **exit 0** で終えること。

```bash
printf '{"decision": "block", "reason": "..."}\n'
exit 0
```

`exit 2` を併記すると stdout の JSON 側が無視されるため、**併用しない**。
`check-command-safety.py` がこの方式で実際に動作している唯一の実証例。

> テストの合格基準を exit code にしていると、**テストは緑なのに実環境では無防備**という
> 状態を見逃す。判定は「実際にブロックされる出力が出るか」で書くこと。

### hook が本当に発火したかを実測する（2026-08-23）

設定が正しいことと、実際に発火していることは別。1コマンドで両方を分けて測る:

```bash
wsl bash -lc "bash ~/bin/verify-hook-matchers.sh --session-id $CLAUDE_CODE_SESSION_ID"
```

終了コードは **0=PASS / 1=FAIL / 2=SKIP（判定不能）** の3値。

**`--session-id` を必ず渡すこと。** `CLAUDE_CODE_SESSION_ID` は Claude Code を動かしている
**Windows 側シェルにしか無く、`wsl bash -lc` の内側へは伝播しない**（実測）。
渡さないと「自セッションを特定できない」として SKIP になる。

> ⚠️ **他セッションの記録で「発火している」と判断してはいけない。**
> `~/.claude/logs/tool-usage-YYYY-MM-DD.csv` には**並行セッション全部**の記録が混ざる
> （2026-08-23 実測で1日7セッション・119件）。session_id で絞らずに件数だけ見ると、
> 自分の hook が死んでいても他人の記録で PASS に見える。2026-08-22 に実際にこれで誤判定した。

**SKIP は「異常なし」ではない**。判定材料が無いという意味なので、理由を読んで対処する:

| SKIP の理由 | 対処 |
|---|---|
| 自 session_id を特定できない | `--session-id` を渡す |
| 自セッションの記録が本日0件 | ツールを1回使ってから再実行（PostToolUse がまだ完了していないレース） |
| WSL⇔Windows の時計がずれている | `sudo hwclock -s` で合わせてから再実行 |

## 自律タスクループ（Stop Hook 応用）

### 概要

GitHub Issue を順番に自動実装するイベント駆動ループ。  
CronCreate が時間トリガーのみなのに対し、Stop Hook を使うことで「前のタスク完了後に次を起動」が実現できる。

### ファイル構成

```
~/.claude/scripts/auto-dev/
├── state.json       # キュー状態（永続）
├── start.sh         # 手動起動エントリポイント
├── next-issue.py    # Stop Hook 本体
└── loop.log         # 実行ログ（自動生成）
```

### 使い方

```bash
# WSL で実行（Issue #76 → #75 の順で自律実行）
bash ~/.claude/scripts/auto-dev/start.sh 76 75

# 状態確認
cat ~/.claude/scripts/auto-dev/state.json

# ログ確認
tail -f ~/.claude/scripts/auto-dev/loop.log
```

### 緊急停止

```bash
python3 -c "
import json
p='/home/yn4416/.claude/scripts/auto-dev/state.json'
s=json.load(open(p))
s['active']=False
json.dump(s,open(p,'w'),indent=2)
print('停止しました')
"
```

### 誤爆防止

- `state.active == false` の時は `next-issue.py` が即 `exit(0)` — 通常の会話終了では何も起きない
- `except` 節で必ず `exit(0)` — Stop Hook がセッション終了をブロックすることはない

### 動作フロー

```
start.sh 76 75
  → state.json: active=true / pending=[76,75]
  → claude --print "Issue #76 を実装して..."
  → [セッション終了]
  → Stop Hook → next-issue.py
      → completed=[76] / pending=[75]
      → claude --print "Issue #75 を実装して..."
      → [セッション終了]
  → Stop Hook → next-issue.py
      → completed=[76,75] / pending=[] → active=false → 完了
```

> 詳細: [2026-05-30_自律タスクループ実装](../../01_DECISIONS/claude-code/2026-05-30_自律タスクループ実装.md)

## PreToolUseでのコマンド書き換え（`updatedInput`パターン）

PreToolUseフックはブロック（`{"decision": "block", ...}`）だけでなく、**ツールの実行直前にその入力を書き換える**こともできる。以下のJSONをexit code 0で標準出力に書くと、`updatedInput`で指定した内容が実際の実行に反映される（セッション再起動不要・live反映）。

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "updatedInput": { "command": "書き換え後のコマンド文字列" }
  }
}
```

**実例（Windows Desktop版限定）**: `path-rewrite.py`は、Bashコマンド文字列内の既知WSLホームパスプレフィックス（`~/projects/`・`~/.claude/`・`/home/yn4416/projects/`・`/home/yn4416/.claude/`の4種のみ＝ホワイトリスト）をUNCパス（`//wsl.localhost/Ubuntu/home/yn4416/...`）に単純文字列置換する。これにより、WSL CLI版で書かれた共有ファイル（handoff/SKILL.md/SSOT）内のパスをWindows Desktop版でも変換なしで実行できる。

> **注意点（実機検証で判明）**: ①`wsl bash -c "..."`でラップしたコマンド内のパスも書き換えの対象になるため、ホワイトリスト導入後は対象パスを`wsl bash -c`でラップする必要自体がなくなる（直接実行すればよい）。②既にUNC形式で手書きしたパスは部分文字列としてホワイトリストに再マッチし二重化することがあるため、UNCパスは手書きせず`~/projects/...`等の表記に統一する。詳細: [2026-06-30_Windows-Desktop版WSLパス変換フック実装](../../01_DECISIONS/claude-code/2026-06-30_Windows-Desktop版WSLパス変換フック実装.md)

## `guard-settings-write`（Task6 α C'案・✅実装済 2026-07-31）

`settings.json` への TOKEN 書込を PostToolUse 内容ベース差分検知で防御する hook。Bash 経由（jq / sed / リダイレクト / `python3 -c` / MCP / hooks 設定）の本体 settings.json 書換も完全スルーする `guard-config-secrets.sh` の盲点を塞ぐ。

| 項目 | 説明 |
|---|---|
| タイミング | PreToolUse(Bash) + PostToolUse(Bash\|Edit\|Write\|MultiEdit\|NotebookEdit) |
| 役割 | **主防御**: PostToolUse で実行前スナップショットと実行後を比較し、監視対象パスに TOKEN 風文字列の**新規追加**を検出 → cp -p 復元 + exit2 + ログ + 通知。**補助**: PreToolUse で Bash 同チェイン内「書込操作 + ネットワーク送信」を事前ブロック（ベストエフォート） |

## hook実行タイミング早見

| イベント | タイミング | 代表例 |
|---|---|---|
| UserPromptSubmit | 発言の送信直後 | 相談フォーマットの注入・モデル語検出時のstatus実測注入・毎ターン日時注入 |
| PreToolUse | ツール実行の直前 | 破壊的コマンドのブロック |
| PostToolUse | ツール実行の直後 | ログ記録・設定同期 |
| Stop | 応答完了時 | 検証宣言チェック・handoff生成 |
| SessionStart | 開始時 | handoff読込・整合チェック |

> 💡 **章の落とし所**: hookを増やすほど起動が遅くなる。目的が「止める」か「記録する」かを決めてから追加する。
